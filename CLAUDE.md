# Hangar

Hangar is a macOS desktop app for running many Claude Code CLI sessions ("agents") at once: a sidebar of agents in folders, up to four terminals in a grid, one git worktree per project per agent, and a read-only code drawer. Sessions live in a separate **session host** process so the app can be reloaded, rebuilt or crash without killing them. The app is meant to be modified by the agents running inside it.

Architecture: `docs/ARCHITECTURE.md`. Platform traps: `docs/GOTCHAS.md` (read it before touching anything that spawns processes).

## Processes

```
Renderer (React, xterm.js)  ⇄ preload (window.hangar) ⇄  Main (Electron; git, state, socket client)
                                                                 ⇅ NDJSON over ~/.hangar/run/host.sock
                                              Session host (system Node + node-pty + @xterm/headless)
                                                                 ⇅ PTY: $SHELL -il → claude …
                                              `hangar` CLI (hooks + agents) ─────────────────────┘
```

|---|---|---|

**Plan 06** added five things. (1) **A new agent from a Linear ticket**: the toolbar's ticket button or ⌘⇧L opens `LinearDialog`; `linear:triage` runs a headless `claude -p` in `src/main/services/linear-triage.ts` (prompt on stdin because `--allowedTools` is variadic; cancellable through `util/exec.ts`'s `signal`; candidates from `repo-discovery.ts`), and pure code in `shared/linear-draft.ts` turns the answer into a `TicketDraft` that prefills `NewAgentDialog`, which runs the create sequence (`project:add` → `folder:create` → `agent:create` → `agent:update`). The two-tool limit is enforced by the argv, not by trusting the model — `--setting-sources '' --strict-mcp-config --mcp-config <Linear only> --tools '' --permission-mode dontAsk --allowedTools <two>`, the measurements that led to each flag are in spec §9 and G74–G76; `triageArgs` pins it in a test. (2) **Removing a non-primary project from an agent** (`agent:inspectRemoveWorkspace`/`agent:removeWorkspace`, `RemoveWorkspaceDialog`), sharing `inspectWorkspace`/`teardownWorkspace` and `InspectionList` with delete so the two cannot drift. (3) Config gained `claudeDefaultArgs` (launch args before the project's and the agent's — the last duplicate `--model` wins, measured), `reposDir`, `triageModel` and `defaultPermissionMode` (where the New Agent dialog's Permission mode starts; never a launch argument). (4) **Resume follows in-session id changes**: `session-registry.ts` adopts a UUID `session_id` from `SessionStart`. (5) **The window reopens where it was closed**: `src/main/services/window-state.ts` (pure fit/fold/load/save) plus the listeners in `src/main/index.ts`, stored in `HANGAR_HOME/window-state.json`, main-owned and deliberately not in `Layout`.

**Plan 07** made that dialog two-way. `src/main/services/linear-mcp.ts` talks to the Linear MCP server **directly over HTTPS with no model at all** — JSON-RPC, `initialize` cached per app run, bodies parsed as either plain JSON or SSE — borrowing the OAuth token Claude Code keeps in the login keychain (`security find-generic-password -s 'Claude Code-credentials'`, the `mcpOAuth` entry whose `serverUrl` matches), read per call, never stored, never logged, never sent to the renderer, and never refreshed, because rotating it would break Claude Code's own Linear connection. Exactly four tools are reachable — `list_issues`, `list_cycles` (a row carries only a `cycleId`, never a number), `list_teams` and `save_issue` — and `save_issue` is called from one place only: the create form's Save. The HTTP client is Electron's **`net.fetch`**, not the global `fetch`, for the system proxy and the OS certificate store (G84), injected so tests reach neither the network nor the keychain. So `⌘⇧L` now lists every ticket assigned to the owner (`linear:myIssues`, cached in `createHandlers`' closure for the app run, `Load more` by a cursor stamped with the cache generation, Done/Cancelled dimmed, `agent exists` focusing the agent that already exists) and can **create** one (`NewTicketForm` → `linear:createTicket`), with `Draft with Claude` (`linear-ticket-draft.ts`) filling only the empty fields from a headless `claude -p` that has **no MCP servers and no tools at all**. Payload parsing, classification, cleaning and the merge are pure code in `shared/linear-issues.ts` — including G81's trap, that a ticket's human identifier arrives as its `id`. Two rules the feature is built around. **Nothing spends Claude usage unless the owner presses something**, so nothing polls, pre-fetches or warms anything. And **the one write is never retried**: `LinearError.outcome` (not its code) says whether a request may have taken effect, and an unknown outcome becomes `LINEAR_CREATE_UNCONFIRMED`, which the form answers with *Check the ticket list* rather than another Save (G83).

**Plan 08** put the ticket picker one level up. **`Whole cycle…`** in ⌘⇧L opens `CycleRun.tsx`: `linear:cycles` fans the existing `list_cycles` out over the teams on the cached FIRST PAGE of the owner's tickets (one read per team per app run, held in `createHandlers`' closure as `cycleRows` — the same rows that put `cycle 32` on a ticket row, so there is one cycle cache and not two), and `linear:cycleIssues` is `list_issues` with `cycle` and `assignee: 'me'`, every page of it, because the tick boxes and the count in the button are statements about a COMPLETE list. **Both are MCP reads with no model in them, and this feature calls `save_issue` nowhere.** Pressing **Create N agents** runs the existing `linear:triage` **one ticket at a time** — never in parallel: each is a `claude -p` at ~33 s and ~$0.22-equivalent, measured — and creates each agent through `src/renderer/lib/create-agent.ts`, which is `NewAgentDialog`'s own four-step sequence lifted out rather than re-implemented, so the two callers cannot drift about `PROJECT_EXISTS`, the folder re-check, a `saved`-then-failed `agent:create` or a notes failure. Its progress recorder binds to one `opId`, because `agent:progress` is a broadcast and a dialog create during a run would otherwise donate its result to a row (G89). Four rules the run is built around: a failed ticket is marked and the next one starts, while a create that SAVED the agent and then failed gets a row of its own that `Retry failed` never picks up — nothing rolls that agent back, so a retry would make a second one; a ticket that already has an agent is skipped BEFORE the look-up, so it costs nothing at all, and is re-checked against `useWorkspace.getState()` again immediately before the create, because an agent can appear from another window during the half-minute look-up (G87); **Cancel run** stops after the ticket in flight and aborts it, and closing the dialog does the same; and `app:diskFree` is read before each look-up, stopping the run under `shared/disk.ts`'s `LOW_DISK_WARN` and quoting `lowDiskText` verbatim — before the spend, not after it. Agents are created **unstarted**, into one `Cycle <n>` folder that `folderNamed`'s re-check makes exactly once across the whole run. Every decision the step makes is pure code in `shared/linear-cycle-run.ts`: the labels (`Cycle 33 · 29 Sep – 12 Oct (current)` — Linear's boundaries are instants at the team's local midnight and `endsAt` is EXCLUSIVE, so the dates are a midday snap and the end is the day before it, G86), the ordering (by start DATE, because cycle numbers are per team), which cycle opens (`currentCycle`, because `isCurrent` is a per-team flag several rows can carry and none need), the tick-box defaults, the plan order and every sentence the step shows. The picker keeps three outcomes apart: no teams is an honest empty list, a partial answer beats a failure, and every team failing throws Linear's own `LINEAR_*` — whose **Retry must send `refresh: true`**, or main's per-team memo hands the same failure back for the rest of the app run.

**Plan 09** added two things that share the pane header, and the signature one of them needs. (1) **A colour spine.** `shared/pane-hues.ts` maps pane index 0–3 to a fixed palette — violet, teal, rose, gold, deliberately clear of the status-dot colours — and `paneHue` answers `null` outside `0..MAX_PANES-1`, never a wrapped colour. **The hue belongs to the pane, not to the agent**, so nothing shuffles while you work and moving an agent to another pane changes its colour. A 3px rail runs down the pane's left edge, full strength when focused and 55% otherwise, beside a `⧉N` chip in the header; it is an absolutely positioned overlay inside the pane's own box, because a border, a padding or a sibling takes 3px from the box the terminal is measured from and turns a repaint into a PTY reflow. The sidebar row of an agent that is in a pane gets the same rail and its `⧉N` chip tinted; a row in no pane gets neither. Hovering a row lifts its pane's rail through `hoveredAgentId` on the ui store, which `AgentRow` writes and never reads (it also clears it on unmount while it is still its own, because React fires no `pointerleave` for a row that vanishes under the pointer), and which `Pane` selects as the BOOLEAN `agentId !== null && s.hoveredAgentId === agentId` (G59/G61 — and without the null guard an empty pane lights up whenever nothing is hovered). (2) **Dictation**, because Claude Code's own voice mode cannot work in Hangar, for two measured reasons: the microphone request comes from `claude` under the launchd-detached session host, which has no responsible app, so macOS denies it without ever prompting (G90); and hold-to-talk needs a key-RELEASE, which xterm.js 6.0.0 cannot report — no kitty keyboard protocol, and no `TERM_PROGRAM` to identify the terminal by (G91). So Hangar listens itself. `mac/dictate/main.swift` is an on-device transcriber (`SpeechAnalyzer`/`SpeechTranscriber`, macOS 26: no network after the first-use model download, no key, no Claude usage) that `scripts/build-dictate.mjs` compiles into `resources/bin/hangar-dictate`. It writes NDJSON on stdout — `ready`, `preparing`, `partial`, `final`, and `error` with `MIC_DENIED`/`NO_MODEL`/`NO_INPUT`/`FAILED` — and reads `stop`/`cancel` on stdin, with SIGTERM and EOF also a cancel. **`shared/dictation.ts` is the one place that knows that protocol and the words**: the line parser (it takes BYTES, so a character split across two reads survives), the reducer `idle → starting → preparing → recording → finalizing → idle`, `toggleRequest`, `textToWrite`, and every sentence the feature shows, spec §4's verbatim — so neither main nor the renderer parses a line or writes a sentence of its own. **Main owns the process** (`src/main/services/dictation.ts`): one helper at a time, single-flighted on the PROCESS HANDLE and never on the reducer being idle — a run is over the moment its final arrives while the helper is still exiting, and a start then is refused with `DICTATION_BUSY`, never queued — with a 10 s ceiling on `stop`, the 120 s cap counted from `ready` in main as well as in the helper, and a SIGKILL for any helper that outstays its run. **The write happens in main, once, and never with a newline.** `createHandlers` binds each run to the agent `dictation:start` named and stamps that `agentId` on every `dictation:event`, which is a broadcast (G89); a `write` outcome goes into that agent's session through the same host message `session:write` sends, after `textToWrite` has turned every control character into a space — run once in the reducer and again at the write itself, whatever produced the outcome — so nothing dictated can submit itself. **Never into a waiting prompt**: the write is keystrokes, and a Claude Code permission menu takes a digit or a letter as a choice, so when the final arrives while that session is `needs-permission` main puts the words on the CLIPBOARD instead and broadcasts a `copied` outcome, which the renderer shows as a sticky `The agent is waiting for an answer, so your dictation was copied instead of typed. Paste it with ⌘V when you're ready.` — the words are neither typed into the menu nor lost. A cancel, an error or an empty final (`Nothing heard.`) writes nothing; a session that stops or exits mid-run cancels the run at once (main hears every registry state change through `onSessionState`), and a final that races a restart is dropped with a warning that never quotes the words. In the renderer, the mic button leads each pane header's button row, disabled with the reason as its tooltip when the agent is not running or another agent is being dictated to; **⌘D** toggles for the focused pane; a pill above the pane's bottom edge shows the live partial and never takes focus; **Escape cancels, in the terminal's own key handler and only while that agent's run is alive** — at every other moment it reaches the PTY, because Claude Code uses it — and **closing the pane cancels the run** (a watcher in `bootstrap.ts`), because nothing left on screen could stop it — as does a renderer reload or crash, the crash past the reload limit included (`services/renderer-crash.ts`). The pill offers `Esc cancels` only where a terminal is mounted to take the key, and main's refusals (`DICTATION_BUSY`, `NOT_RUNNING`) reach the screen as `dictationRefusal`'s sentences, never in main's own words. (3) **A stable signature.** `npm run app` carries the helper to `Contents/Resources/app/resources/bin/hangar-dictate` — the checkout's own relative path under the packaged `repoRoot`, so main resolves it with one `join` — refuses to package without it, and ends with `scripts/sign.mjs`: the helper first, then the bundle, with the self-signed `Hangar Local Signing` certificate (`HANGAR_SIGN_IDENTITY` overrides) resolved to its SHA-1, no hardened runtime, and `codesign --verify --deep --strict` plus the `Authority=` of both checked afterwards. electron-builder's ad-hoc signature changed with every build and took the microphone grant with it; the certificate's does not. It is untrusted, so macOS lists **0 valid identities** and electron-builder cannot use it, but codesign signs with it (G93). **Only the DEFAULT certificate being absent is a warning** — a fresh checkout still builds, ad-hoc, and dictation then asks for the microphone again after every install; a `HANGAR_SIGN_IDENTITY` that names no certificate, or a `security` look-up that fails with anything but exit 44 (not found), fails the build (`identityVerdict` in `scripts/signing.ts`).

**Nothing in the plans is unbuilt.** What is left is not code but *unverified* behaviour, and it is
listed in one place: **`docs/RELEASE-CHECKLIST.md`** — the manual items nobody has driven by hand, and
the things the automated gates provably cannot see. Read it before shipping, and before assuming any
manual behaviour works. Two known approximations in the shipped Diff tab are deliberate and recorded in
`PROGRESS.md`: a **rename** is diffed as the new path against a base that lacks it, so it renders as a
whole-file addition (bannered as such — carrying `origPath` through is P4-2h/P4-3e's deferred work), and
`collapseUnchanged`/scrolling/focus are unproven by the tests because jsdom has no layout engine. One
gap is **owed rather than deferred**: `TerminalView`'s attach is not idempotent, so the app cannot run
under `<StrictMode>` — `src/renderer/main.tsx` therefore does not use it. Measured on React 19.2.8, one
StrictMode mount sends **2** `session:attach` calls and **0** `session:detach` (G26).

## Commands

- `npm run dev` — app with `HANGAR_HOME=~/.hangar-dev` (safe for hacking; own host, socket, worktrees)
- `npm run dev:real` — app against `~/.hangar` (the owner's real data)
- `npm test` — vitest + `scripts/smoke-host.mjs`; `npm run test:unit` for vitest only
- `npm run typecheck`, `npm run lint`
- `npm run host` — run the session host in the foreground (needs `HANGAR_HOME`)
- `npm run app` — build `dist/mac-arm64/Hangar.app` (~325 MB). It compiles the dictation helper first (`build:dictate`), and three assertions run between the bundle and the package, because every one of these failures is invisible until the app is opened: the Electron side must require nothing from `node_modules` (it ships none), every bare import in `host/`, `cli/` and `shared/` must be listed in `electron-builder.yml`'s `extraResources`, and `resources/bin/hangar-dictate` must exist, be executable and be carried to `app/resources/bin` — so a Mac with no Swift toolchain cannot produce the app at all, rather than producing one without dictation. It ends by **signing** it (`scripts/sign.mjs`, with `Hangar Local Signing` or `HANGAR_SIGN_IDENTITY`, verified with `codesign`); a missing DEFAULT certificate only warns and leaves the ad-hoc signature, which costs the microphone grant at every install, while an explicit `HANGAR_SIGN_IDENTITY` that is not there, or a keychain `security` cannot read, fails the build. To verify the artefact rather than the build, `HANGAR_SMOKE_ROOT="$PWD/dist/mac-arm64/Hangar.app/Contents/Resources/app" node scripts/smoke-host.mjs` runs the full host+CLI smoke against the packaged tree (the path must be **absolute** — the relative form fails falsely with `timeout waiting for rename event`, because the smoke's PTY runs in `/tmp`) — that is what proves `node-pty` loaded under the **system** Node's ABI and not Electron's (G2), and that `bin/hangar` resolves from inside the `.app`.
- `npm run build:dictate` — compile `mac/dictate/main.swift` into `resources/bin/hangar-dictate` with `xcrun swiftc` (Xcode command line tools; without them it skips with the one command that installs them). A checkout's `npm run dev` finds the helper there; without it the mic button is still enabled, and pressing it ends the run at once with the toast `Dictation is not built. Run npm run build:dictate.`
- `npm run build` — `electron-vite build` only (what `npm run app` runs straight after the helper, and the last of the five gates)
- `npm run start` — `scripts/dev.mjs --built`: `electron .` against `out/` instead of the Vite dev
  server. **It defaults `HANGAR_HOME` to `~/.hangar`, the owner's real profile** — unlike `npm run dev`.
  Set `HANGAR_HOME` yourself if you did not mean that.

**The installed app carries its own copy of `host/`, `cli/` and `shared/`** (and of the dictation
helper, at `resources/bin/hangar-dictate` beneath the same root) at
`Hangar.app/Contents/Resources/app`, because that half runs as raw `.ts` under the **system** Node with
no build step (`src/main/index.ts` sets `repoRoot = join(process.resourcesPath, 'app')` when
`app.isPackaged`). So editing those directories does **not** change `/Applications/Hangar.app` — re-run
`npm run app` and re-install. `npm run dev`, `npm run dev:real` and `npm run start` all run out of the
checkout (`app.isPackaged` is false), so there the edit is live.

The UI is React under `src/renderer`; stores are the only place that hold snapshot state. Terminal
instances live in `src/renderer/lib/terminal-registry.ts`.

## Rules

1. Never build a shell command from strings. Use `execFile(cmd, [args])`. Two places handle shell strings and they are defended differently: the **PTY startup command** is built with `shared/shell-quote.ts` — arguments only; the `claude` command word stays bare so a user's alias resolves — **and** must have control characters stripped first, because quoting cannot contain a byte the line editor eats before the parser runs (see G33). *(That composer is `src/main/services/claude-launch.ts`, built in Plan 02: `composeStartupCommand` is `claude ${shellJoin(args.map(stripControlChars))}`, and `shellQuote` wraps the hook binary path.)* **`postCreate`** is user-authored and is deliberately *not* quoted: it is passed as a single argument to `$SHELL -ilc`. Wrapping it would turn `npm ci && npm run build` into one unrunnable word.
2. Never expose `ipcRenderer`; the renderer only gets `window.hangar.invoke/on`. Every IPC payload is validated with the zod schema in `shared/ipc-schemas.ts`.
3. `node-pty` is imported **only** in `host/`. Never add a native dependency to `src/main` (Electron's Node ABI differs from the system's).
4. In `host/`, `cli/`, `shared/`: relative imports end in `.ts`; CommonJS packages are default-imported; no `enum`/`namespace`/parameter properties. These dirs run without a build.
5. Every behaviour change comes with a test next to the module (`*.test.ts`). Run `npm test` before saying anything is done.
6. Pin dependency versions from the plans. `vite` stays on 7.x and `typescript` on 5.9.x (see GOTCHAS). `npm view <pkg> version` is not a pin — `latest` regularly breaks the pinned stack, and several of these packages declare no peer ranges at all, so npm will not warn you.
7. Working on Hangar from inside Hangar: create an agent for this repo, run `npm run dev` in its terminal — it uses `~/.hangar-dev`, so the instance you are sitting in is untouched.
8. Commits are plain conventional commits in the owner's name. Never add `Co-Authored-By` or any AI attribution to commits, files or docs. Never `git reset --hard` (stash instead), never force-push, and never merge into `main` unless the owner says so.
9. `shared/` must import nothing raw Node cannot load — no `electron`, no `node:*` in a **source** file (its own tests may). `shared/module-load.test.ts` enforces the Node half by importing every file in a child process. `src/renderer/` has the same ban and it is enforced by the **`no-restricted-imports` block in `eslint.config.mjs`**, with `src/renderer/boundary.test.ts` asserting that block still bites. `tsconfig.web.json`'s `"types": []` does **not** enforce this and never did — it suppresses automatic *global* `@types` inclusion only, so an explicit `import { ipcRenderer } from 'electron'` in `src/renderer/` resolves through `node_modules` and passed `tsc`, `eslint` and `npm run build` all three (measured before the rule was added). Electron-only code belongs in `src/main`.
10. Debugging the app: `ELECTRON_ENABLE_LOGGING=1 npm run dev` is **silently inert** — `scripts/dev.mjs` strips every `ELECTRON_*` variable on purpose (G1). Edit the script temporarily if you need one.

## Recipes

- **Add an IPC request:** add the key to `IpcRequests` in `shared/ipc-contract.ts` → add its zod schema in `shared/ipc-schemas.ts` → add the handler to `createHandlers` in `src/main/ipc/handlers.ts` (`register.ts` binds every key in `IPC_REQUEST_KEYS` automatically, so there is nothing to register by hand) → call it from the renderer via `api.invoke('the:key', payload)`. `shared/contract.test.ts` fails until schema and handler both exist.
- **Add a host message:** extend `ClientMessageSchema`/`HostMessage` in `shared/host-protocol.ts` → handle it in `host/server.ts` `handle()` → add a case to `host/server.test.ts`.
- **Add a CLI command:** create `cli/commands/<name>.ts` exporting `run<Name>(args, ctx)` → register in `cli/run.ts` and `USAGE` → test in `cli/commands/commands.test.ts`.
- **Add a status transition:** edit the table in `shared/status.ts` and the matching case in `shared/status.test.ts`.
- **Add a drawer tab:** create `components/drawer/<Name>Tab.tsx` taking `{ agent, workspace }` → add the id to `Layout.drawerTab` (`shared/types.ts` **and** `shared/workspace-schema.ts`'s `LayoutSchema`/`LayoutInputSchema`, which are a hand-maintained mirror) → render it in `Drawer.tsx` → add the tab to the `drawer-tab` entry of **`SHORTCUTS`** in `lib/keymap.ts` — chord, `does` text and `section` — which is what binds the key AND what puts it in the ⌘/ cheatsheet and in the drawer/pane-header tooltips. `tsc` does **not** catch a missing one here: a new drawer tab reuses the existing `drawer-tab` action kind, so the `Record` stays complete and the tab simply ends up with no shortcut and no cheatsheet row. (A whole new `KeymapAction` kind IS caught — `SHORTCUTS`, `WORKS_IN_TEXT_FIELD` and `OWNED_BY_CODE_EDITOR` are all `Record`s over the union, and the first takes a non-empty tuple so `[]` fails too.) The tab is only mounted while it is the selected tab and the drawer is open, so per-tab polling belongs in the tab's own effect cleanup — that is what makes "never refreshes while hidden" (§12.5) true rather than a `visible` prop nothing passes as false.
- **Add a dialog:** *(a floating PANEL is not a dialog and does not follow this recipe — see the note at the end)* render it from `DialogHost.tsx`'s exhaustive `switch` (a new `DialogState` member fails to compile there rather than rendering nothing) → wrap the body in `ui/Dialog.tsx` → pass `initialFocus` naming the control that should have focus. Do **not** use `autoFocus`: it is a measured no-op inside a `<dialog>` opened with `showModal()`, and the header Close button silently takes focus instead (G62). If a **shortcut** opens it, also name it in **`OPENS_DIALOG`** (`lib/keymap.ts`) — that is the one table that makes the key a toggle, so the combo that opened the dialog closes it while every other shortcut stays inert behind the modal. `tsc` forces a new `KeymapAction` kind to be given a row there but **cannot** force it to be the right one, since `null` is a legitimate value; the guard that can is `keymap.test.ts` → "OPENS_DIALOG names the dialog each action actually opens", which cross-checks the table against what `applyKeymapAction` really opens.

  **The one exception, and how to tell you have one.** Every member of `DialogState` is treated as a modal: `installKeymap` stands the WHOLE shortcut table down while `ui.dialog !== null`. That is right for something you answer and dismiss, and wrong for something you leave open while you work — the ⌘/ cheatsheet was a `<dialog>` until X5-3, and being one made every shortcut it documents inert on the screen documenting it. If the thing you are adding is a panel rather than a modal, it does not go in `DialogState` at all: give `ui` its own flag (`shortcutsOpen`), mount it from `App.tsx` as a sibling of the layout — never inside `main` or a `Pane`, whose `onMouseDownCapture` would swallow a drag (G60) — put its toggle in `applyKeymapAction` beside `toggle-sidebar`/`toggle-drawer` with `null` in `OPENS_DIALOG`, and handle Escape on the panel's own `onKeyDown` (never on `window`: Escape belongs to the terminal). **G62 does not apply to it** — there is no `showModal()` and so no dialog focusing steps — and a panel should generally take no focus at all, which is what lets the user try a shortcut while reading it. Geometry that should survive a restart belongs in `Layout` (`shared/types.ts` **and** `shared/workspace-schema.ts`'s hand-maintained mirror, where a field new to an existing `workspace.json` needs `.default(...)` or the whole file is classed corrupt on the first load), clamped by a pure function in `shared/layout.ts` — `normalizeLayout` cannot see the window, so a viewport clamp has to be applied where the panel is drawn. `components/ShortcutsPanel.tsx` is the worked example.
